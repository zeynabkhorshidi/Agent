# اجرا و استقرار

## توسعه

اجرای README در Python 3.12 آزمایش شده است. مسیر نسبی `SELLORA_DB` نسبت به دایرکتوری اجرای سرور است؛ مسیر مطلق برای استقرار توصیه می‌شود. migration هنگام startup تکرارپذیر اجرا می‌شود. فقط اگر جدول محصولات خالی باشد چهار کالای نمونه seed می‌شوند. شروع مجدد قیمت و موجودی موجود را بازنشانی نمی‌کند.

متغیرهای اجرایی: `SELLORA_ENV`، `SELLORA_DB`، `SELLORA_ADMIN_PASSWORD`، `SELLORA_SALES_PASSWORD`، `SELLORA_OPERATOR_PASSWORD`، `COOKIE_SECURE`. `STT_BASE_URL` و timeout/حجم تنظیمات اجرایی Adapter صوت هستند. سایر نام‌های منابع تجارت قرارداد اتصال آینده‌اند. برای Dev و Prod نشانی صوت جدا مستند شده است؛ قرارداد HTTP فایل اکنون دریافت شده؛ URL پایه قابل تنظیم و سمت سرور است.

## کانتینر

Dockerfile با کاربر غیرریشه و healthcheck، Compose با volume پایدار و bind محلی ارائه شده است. تصویر در محیط تحویل واقعاً ساخته شده است. در شبکه دارای گواهی خصوصی:

```sh
docker build --secret id=proxy_ca,src=/path/to/company-ca-bundle.pem -t sellora:local .
```

مسیر گواهی عمومی است؛ کلید خصوصی ندهید. گواهی فقط در مرحله نصب mount می‌شود و وارد image نمی‌شود. TLS verification خاموش نمی‌شود. برای محیط cloud این جلسه از bundle معتبر سیستم استفاده شد. Docker Compose معمولی برای شبکه دارای CA استاندارد است؛ اگر پراکسی اختصاصی دارید نخست build بالا را اجرا و سپس کانتینر همان تصویر را با پیکربندی مناسب راه‌اندازی کنید.

## سلامت و داده

`GET /api/health` وضعیت جداگانه پایگاه، سفارش محلی، STT، TTS، مدل و کاتالوگ را برمی‌گرداند. «نیازمند قرارداد» با سالم اشتباه گرفته نمی‌شود. وضعیت شبکه و circuit صوت در `/api/voice/status` جدا بررسی می‌شود؛ health سرویس شرکت صحت استنتاج را اثبات نمی‌کند. healthcheck کانتینر سلامت پایگاه را بررسی می‌کند، نه آمادگی تجاری.

پشتیبان سازگار با WAL:

```sh
python -m sellora.maintenance backup --destination /secure/path/sellora-backup.db
python -m sellora.maintenance purge --transcript-days 7
```

این فرمان‌ها نشست مشتری را روی دستگاه ذخیره نمی‌کنند. فایل DB و نسخه‌های پشتیبان شامل داده شخصی‌اند؛ سطح دسترسی فایل و رمزگذاری دیسک بر عهده استقرار است. تنها داده ساختگی در نسخه توسعه استفاده شود. پاک‌سازی رونوشت و مرور منقضی پیاده شده؛ حذف کامل مشتری و الزامات نگه‌داری مالی باید طبق سیاست شرکت تکمیل شوند. صوت اصلاً ذخیره نمی‌شود. فعال‌سازی نگه‌داری آینده بدون رضایت مستقل مجاز نیست.

## گذر به عملیات واقعی

وضعیت فعلی تک‌نمونه و توسعه است؛ production در startup مسدود می‌شود. پیش‌نیازها:

- OTP/SSO واقعی، نشست‌های فردی و نقش‌های سازمانی، محدودیت نرخ و قفل ورود، مدیریت امن رازها.
- اتصال منابع مشتری، قیمت، موجودی و سفارش با بررسی مجوز و قرارداد retry/idempotency سمت ERP.
- انتقال schema و repository layer به PostgreSQL، migration نسخه‌دار برای تغییرات آینده، آزمون چند worker و رزرو موجودی. جایگزینی فایل SQLite با DSN به‌تنهایی کافی نیست.
- HTTPS روی دامنه شرکت و reverse proxy معتبر؛ `COOKIE_SECURE=true`، محدودیت بدنه درخواست، timeout و WebSocket upgrade تنها پس از قرارداد صوت.
- شبکه مجاز بک‌اند به IPهای داخلی از VPN یا زیرساخت شرکت؛ دسترسی مرورگر به IPهای داخلی طراحی نشده است.
- metric و tracing بدون PII، محدودیت نرخ، alert برای خطای هر وابستگی و تست بار با داده کنترل‌شده.
- STT اکنون Adapter فایل دارد؛ TTS و barge-in گفت‌وگوی تمام‌دوطرفه همچنان نیازمند قراردادند. پاسخ دیررس و لغو محلی پیاده شده است. health مستقل از `navigator.onLine` است.
- اگر ذخیره سند/صوت نیاز شد، S3 و سیاست retention، signed URL و مجوز فردی دریافت.

برای استقرار واقعی حذف حفاظ production، بدون تکمیل این اتصال‌ها و آزمون‌ها توصیه یا ادعا نشده است. Docker آماده ساخت است؛ Docker به معنی اتصال سازمانی یا انتشار عملیاتی نیست.

## محدودیت درخواست صوت

حد حجم برنامه پیش‌فرض ۲۵ مگابایت است؛ reverse proxy باید بدنه multipart را با سقف متناسب (مثلاً ۲۶ مگابایت) و timeout آفلاین ۱۲۰ ثانیه محدود کند. فایل آپلود موقت توسط parser و پس از پردازش بسته می‌شود؛ فایل صوت به فضای اسناد یا DB نوشته نمی‌شود. متن تبدیل‌شده حدود ده دقیقه با پاک‌سازی سی‌ثانیه‌ای برای retry نوبت نگه‌داری می‌شود. حذف رونوشت ارسالی در مکالمه مستقل است. سیاست نگه‌داری سرویس STT شرکت باید جدا بررسی شود.
