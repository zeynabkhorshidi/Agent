# بررسی خطای اتصال صوت شرکت

## ناسازگاری قطعی در فایل‌های استقرار ارسالی

Dockerfile ارسالی `uvicorn app:app --host 0.0.0.0 --port 8123` را اجرا می‌کند، اما compose ارسالی نگاشت `127.0.0.1:8000:8000` دارد. در آن compose، مقصد داخلی به listener واقعی اشاره نمی‌کند. راهنمای ارسالی هم صریحاً به لزوم تغییر mapping اشاره کرده است.

فایل جایگزین `integrations/stt/docker-compose.fixed.yml` آماده است. مسئول مجاز باید آن را **کنار Dockerfile اصلی پروژه STT** بگذارد و در همان پوشه اعتبارسنجی کند:

```sh
docker compose -f docker-compose.fixed.yml config
```

این فایل برای سرویس مستقل STT است، نه Dockerfile خود Sellora. کد کامل سرویس و مدل باید در همان مخزن STT موجود باشند. استقرار آن در شرکت در این کار انجام نشده است.

در Kubernetes هم باید targetPort با listener واقعی 8123 تطبیق داده شود؛ شماره بیرونی NodePort می‌تواند همچنان 30089 بماند. manifest زنده در دسترس نیست، بنابراین علت قطعی رخداد فعلی به این mapping نسبت داده نمی‌شود. اجرای محلی امن این compose، STT را روی localhost:8123 در اختیار backend هم‌میزبان می‌گذارد؛ برای دسترسی شرکت به reverse proxy/Service مجاز نیاز است.

healthcheck فقط سلامت HTTP را می‌سنجد و ادعای آماده بودن Google یا inference مدل نمی‌کند.

## تشخیص قطع اتصال پیش از پاسخ

اگر Test-NetConnection موفق باشد ولی curl برای HTTP با خطای 56 و برای HTTPS با خطای 35 و کد 000 تمام شود، اتصال TCP برقرار شده ولی پاسخ HTTP معتبر دریافت نشده است. باز بودن پورت، سلامت API یا مدل را اثبات نمی‌کند. از این نتیجه نمی‌توان خرابی Whisper، Google، میکروفون یا FFmpeg را قطعی دانست. تغییر خودسرانه پروتکل یا پورت نیز راه‌حل تأییدشده نیست.

ممکن است سرویس پشت پورت، reverse proxy، نگاشت پورت یا کنترل شبکه پس از handshake اتصال را ببندد. تفکیک نهایی به بررسی سمت استقرار نیاز دارد. اگر TLS به hostname/SNI نیاز دارد، نام دامنه باید از مسئول سرویس دریافت شود؛ با خاموش کردن بررسی گواهی نمی‌توان آن را حل کرد.

برای مسئول مجاز سرویس، نشانی تنظیم‌شده، نتیجه TCP، خطای curl و وضعیت /health و /openapi.json را تهیه کنید. گزارش خصوصی شبکه کاربران نباید در مخزن عمومی قرار گیرد.

## بررسی در محل استقرار توسط مسئول مجاز

۱. مشخص شود پورت خارجی واقعاً به همین API وصل است. مستند ارسال‌شده، پورت 8123 را برای اجرای محلی معرفی کرده و شماره‌های قدیمی 30053/30062 را با عنوان previous deployment آورده است. آن‌ها جایگزین خودکار پورت قطعی 30089 نیستند.
۲. از داخل همان host/container/pod، روی پورت واقعی listener، پاسخ سلامت و OpenAPI بررسی شود. پورت داخل image مطابق README برابر 8123 است؛ نگاشت خارجی باید با image واقعاً مستقر تطبیق داده شود.
۳. اگر Kubernetes استفاده شده، Service، targetPort، endpointهای سالم، readiness و لاگ pod بررسی شوند. باز بودن NodePort به‌تنهایی سلامت برنامه داخل pod نیست.
۴. پس از دسترسی معتبر، offline_model_files_present و مسیر mount مدل بررسی شوند. health، inference واقعی یا دسترسی Google را تست نمی‌کند.
۵. CTranslate2 باید فایل کامل model.bin و فایل‌های سازگار config/tokenizer داشته باشد؛ فقط JSONها کافی نیستند. FFmpeg باید در مسیر تعریف‌شده سرور نصب باشد. قالب Vosk با این پروژه سازگار نیست.
۶. خروجی آنلاین صفحه خود سرویس طبق README از Web Speech مرورگر است؛ کار کردن آن، سلامت Google file-upload API روی سرور را اثبات نمی‌کند.

فایروال، پراکسی یا اعتبارسنجی TLS نباید برای پنهان کردن خطا غیرفعال شوند؛ سرویس و مسیر مجاز باید درست تنظیم شوند.

## اصلاحات Sellora

- علت‌های آنلاین و آفلاین، کد HTTP و وضعیت مدار جدا حفظ می‌شوند؛ خطای کلی all_unavailable دیگر علت هر دو را حذف نمی‌کند.
- قطع/reset، DNS، رد اتصال، پراکسی، TLS، timeout، مسیر اشتباه و برخی خطاهای شناخته‌شده مدل/پردازش صوت از هم تفکیک می‌شوند. متن خام خطا، رمز، صوت و رونوشت وارد گزارش خطا نمی‌شوند.
- مشتری پیام قابل اقدام و شناسه پیگیری دریافت می‌کند. جزئیات فنی فقط در audit و مسیر مجاز مدیریت است.
- گزارش /health نامعتبر با OpenAPI معتبر، سلامت سرویس تلقی نمی‌شود. نبود مقدار فایل مدل «نامعلوم» است و به نبود قطعی مدل تعبیر نمی‌شود.
- متن سلام اولیه بین مرورگر و بک‌اند یکسان شد؛ متن جدید قبلاً در مسیر TTS رد می‌شد.
- CSP فقط برای پخش رسانه اجازه blob می‌دهد تا پاسخ صوتی دریافت‌شده قابل پخش باشد؛ سیاست اسکریپت باز نشده است.

## ابزار همان سیستم کاربر

`check-voice-windows.cmd` را اجرا کنید. اکنون گزارش کامل و بدون اسرار در پنجره و `data/stt-diagnostics.json` نوشته می‌شود. این ابزار با همان HTTP client و تنظیمات پراکسی Sellora کار می‌کند؛ پراکسی مرورگر لزوماً با آن یکسان نیست.

پس از درست شدن سلامت سرویس، برای تست inference با یک صوت غیرحساس انتخابی:

```powershell
.\.venv\Scripts\python.exe -m sellora.diagnostics --audio "C:\path\test.wav"
```

این گزینه فایل انتخابی را صریحاً به هر دو API مستند می‌فرستد. فایل و متن تشخیص در گزارش ذخیره نمی‌شوند؛ فقط موفقیت و متادیتای پردازش ثبت می‌شود. اجرای معمول ابزار، هیچ صوتی ارسال نمی‌کند.

نشانی سرویس در STT_BASE_URL داخل .env باقی می‌ماند. بعد از اصلاح تأییدشده نشانی یا گواهی، Sellora باید دوباره اجرا شود؛ شماره پورت یا پروتکل بدون تأیید مسئول سرویس تغییر نکند.

## نتیجه اعتبارسنجی نسخه اصلاح‌شده

۹۵ آزمون unittest روی این نسخه موفق شدند، بدون شکست یا skipped؛ شامل بازتولید reset در هر دو مسیر، حفظ علت بعد از باز شدن مدار، حفظ کد HTTP بدون افشای متن خام، تشخیص سلامت نامعتبر، اعلام جداگانه نبود فایل مدل، تست انتخابی inference بدون ذخیره رونوشت و کنترل دسترسی گزارش مدیر.

آزمون Chromium با WAV کنترل‌شده نشان داد پخش blob شروع و تمام می‌شود و نقض CSP ندارد. آزمون مجوز سلام اولیه نیز موفق بود. این‌ها دقت STT یا سلامت TTS واقعی شرکت را تأیید نمی‌کنند. گزارش‌ها در `docs/evidence/voice-repair/` هستند.

فایل Compose جایگزین با دستور `docker compose config` اعتبارسنجی شد: پورت داخلی و healthcheck هر دو 8123 و نگاشت محلی 127.0.0.1:8123 است. این بررسی، build یا استقرار واقعی مدل شرکت نیست.
